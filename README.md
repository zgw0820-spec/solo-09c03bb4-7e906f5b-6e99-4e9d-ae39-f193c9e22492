# 微批显存演练（FastAPI + PyTorch，CPU）

一个用于演示「显存不足时缩小微批继续训练」的网页小工具。内置 96 个二维三分类样本
和线性分类器，在 CPU 上用带动量的 SGD 训练，并逐次对照同初值、同样本顺序的整批训练。

## 启动

```bash
docker compose up --build
# 浏览器打开 http://localhost:8000
```

本地直接运行（需 Python 3.11 + 依赖）：

```bash
pip install -r requirements.txt
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

## 页面功能

- **训练设置**：每次更新的样本数 `B`、初始微批大小 `m0`、更新次数、学习率、动量、随机种子。
- **显存演练**：
  - 「从第几次反传起收紧」：从该次反传开始，单个反传最多处理上限个样本；填 `0` 表示关闭演练。
  - 「微批样本上限」：可为 `0`。单个反传处理样本数超过上限即模拟显存不足。
- **样本与分类器**：内置样本散点图，三个类各 32 个样本。
- **运行摘要**：完成更新数、反传次数、缩批次数、参数/动量最大绝对差、停止原因。
- **逐次对照表**：每次更新展示原定样本 ID（原顺序）、反传序列（`#序号 大小 ✓` /
  `OOM→新大小` / `✗`）、参数更新次数，以及参数和动量的最大绝对差。

## 语义（与实现一致）

1. 每次更新的样本列表由 `(更新序号, B, 随机种子)` 唯一确定，缩批**不改变**样本集合与顺序。
2. 微批按原顺序连续切分，损失按 `len(chunk)/B` 缩放，等价于每个样本权重 `1/B`。
3. 每次更新只调用一次 `optimizer.step()`，参数与动量各更新一次。
4. 超限的微批会先为前 `min(上限, 微批大小)` 个样本**真实执行一次反传**（梯度真的写入），
   然后抛出 `SimulatedOOM`；引擎回滚该微批的梯度写入（此前已成功的微批梯度保留），
   把微批大小对半缩小且不超过上限后重试。
5. 若缩小到 1 个样本仍超限，训练停止在**上一次完整更新**之后；停止的这次更新不执行参数更新。
   如果第 1 次更新就失败，则没有任何完整更新。
6. 参考路径对每次更新做一次整批反传 + 一次同样的 SGD 动量更新，逐次比较参数与动量的
   最大绝对差。

## API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/` | 训练页面 |
| GET | `/api/dataset` | 内置样本、类别统计、散点坐标、默认参数 |
| POST | `/api/train` | 运行演练，返回逐次对照结果 |
| GET | `/api/health` | 健康检查 |

`POST /api/train` 请求体示例：

```json
{
  "samples_per_update": 8,
  "initial_micro_batch": 8,
  "updates": 6,
  "lr": 0.2,
  "momentum": 0.9,
  "seed": 1234,
  "oom_start_backward": 3,
  "oom_cap": 2
}
```

## 已知限制

- 显存不足是**模拟**的（按样本数上限触发），不是真实 CUDA OOM；训练始终在 CPU 上。
- 对比参考路径与演练路径共享同一进程内的浮点运算，差异为浮点累积误差量级（~1e-8），
  页面以 `1e-6` 为“一致”阈值。
- 未做持久化，刷新页面后需重新运行；没有用户/任务隔离。
